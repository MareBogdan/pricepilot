# Phase 3 annotation runbook

One page, for running an actual labelling sitting. Read this before pressing any key in the tool.

## Starting a sitting

1. From the repo root: `make annotate` (Windows: `.\make.ps1 annotate`). This serves the repo
   root over `http://localhost:8010/` — the tool fetches its data files with `fetch()`, which
   `file://` blocks (CORS), so it cannot be opened by double-clicking the HTML file.
2. Open **http://localhost:8010/tools/annotate.html** in a browser.
3. If `Resumed: N decisions already recorded on this browser/machine` appears under the top bar,
   you're continuing a prior sitting on this same browser profile — nothing to do, just keep going.

## Keys

| Key | Action |
|---|---|
| `M` | Match — same purchasable unit |
| `N` | No match — different unit or product |
| `S` | Skip / uncertain — a real answer, not a failure. A reason strip appears after; press `1`-`5` to tag why (optional) |
| `U` | Undo the last decision |
| `F` | Flag the current pair (after deciding it) — e.g. worth a second look |
| `C` | Confirm the suggested label — **TRAIN/VAL pairs only, never shown on TEST pairs** |
| `E` | Export all decisions to a downloaded JSON file |
| `I` | Import a previously exported JSON file (refuses if it doesn't match the currently loaded queue/split) |

## Blind TEST first, then assisted TRAIN/VAL — and why

The queue is now ordered so **all 300 TEST pairs come first**, with no suggestion ever shown, and
**all 697 TRAIN_VAL pairs come after**, each showing the rules engine's suggested label (`C` to
confirm it, or `M`/`N`/`S` to override). A full-width banner appears once, at the exact moment the
TEST phase ends, telling you the assisted phase is starting.

**Why this order, specifically:** the headline accuracy number this whole phase produces is
computed from the TEST labels alone. If TEST and TRAIN_VAL were mixed (as they were before this
session), you'd spend hundreds of TRAIN_VAL decisions absorbing the rules engine's habits before
reaching many of the TEST pairs — and that anchoring would leak into labels that are supposed to
be your independent judgement. Labelling TEST first, while nothing has primed you yet, keeps that
number honest. There is no way to jump back to TEST once you're in TRAIN_VAL — sequential only, by
design.

The progress header shows which phase you're in and how many pairs are left in THAT phase — use
this, not the overall done/total count, to gauge how much blind labelling remains.

## Export cadence

**Export after every sitting, and at least every 100 decisions.** `localStorage` only survives on
this one browser, this one machine — it is not a backup.

1. Press `E`. Save the file as `docs/learned/labels/labels-YYYYMMDD-HHMM.json` (use the actual
   date/time of the export).
2. Run, in **Git Bash** (glob expands naturally):
   ```
   uv run python scripts/ingest_labels.py docs/learned/labels/*.json
   ```
   In **PowerShell**, wildcards aren't expanded for you — pass the resolved file list instead:
   ```powershell
   uv run python scripts/ingest_labels.py (Get-ChildItem docs/learned/labels/*.json).FullName
   ```
   This re-validates every export against the frozen queue and committed split file, merges them,
   writes `docs/learned/phase3-labels.json`, and prints/writes a QA report
   (`docs/learned/phase3-label-qa-<date>.md`).
3. Commit **both** the new export file under `docs/learned/labels/` and the regenerated
   `docs/learned/phase3-labels.json` (and the QA report) in the same commit.

**These exports are the most valuable artefact in this repo.** They are the one thing that cannot
be regenerated by running a script again. `docs/learned/labels/*.json` is **committed, never
gitignored** — every export, from every sitting, stays in git history permanently, even after
`ingest_labels.py` has merged it, so nothing is ever a single point of failure.

**Do not re-run `scripts/split_annotation_queue.py` once you've started exporting.** Every export
embeds the split file's own SHA-256 at export time, and `ingest_labels.py` hard-refuses ANY export
whose recorded hash doesn't match the currently committed `phase3-annotation-split.json` — even a
purely additive change to that file. If it ever needs to change mid-labelling, that's an
architecture decision (CLAUDE.md §4), not something to do unprompted.

## If the browser profile is cleared

Nothing is lost as long as you exported before it happened. Open the tool fresh, press `I`, and
pick your most recent export file (from `docs/learned/labels/`, or wherever you saved it). Import
refuses anything recorded against a different queue/split file than the one currently loaded, so
it's always safe to try.

## Never open this file while labelling

`docs/learned/phase3-test-split-reference-predictions.json` holds the rules engine's predicted
label for every TEST pair. It exists for offline evaluation only, is never fetched by
`tools/annotate.html`, and opening it yourself while labelling TEST would defeat the entire point
of the blind design. Leave it alone until every TEST decision is made.

## The pilot stop

After your first **100 TEST decisions**, the tool shows a pilot report (M/N/S counts, skip
reasons, median decision time, tier mix vs. the full queue) and pauses. At that point:

1. Export (`E`).
2. Ingest: `uv run python scripts/ingest_labels.py docs/learned/labels/<your-export>.json`.
3. **Bring the printed QA report to the architect before continuing.** This is the first real
   measurement of CLAUDE.md §7's assumed 200-pairs/hour throughput, and the first real human S
   rate — both currently unmeasured. Don't burn the remaining ~900 pairs on a pace or convention
   gap that a 100-pair check could have caught first.
